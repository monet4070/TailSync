# Iroh 远程配对

- 状态：已实现
- 适用实现：线协议 v4、macOS SwiftUI、Windows Tauri
- 入口：设置 → 连接与设备 → 远程 Iroh 配对

## 用户流程

1. 两台设备都把连接方式设为“自动”。
2. 在已运行的设备上点击“创建邀请链接”，复制生成的 `tailsync://pair/v1/...` 链接。
3. 把链接交给新设备。Windows 和 macOS 都注册了 `tailsync` 链接；系统能唤起 TailSync 时会自动打开设置页。也可以在设置页的“使用邀请链接”中手动粘贴。
4. 新设备检查链接后点击“开始配对”。
5. 两端仍需核对六位验证码和设备指纹，并分别确认；邀请链接不会替代 Noise XX 身份确认。
6. 配对完成后，两端保存对方的固定公钥，后续同步不再需要邀请链接。

链接有效期为 120 秒，同一设备同时只保留一个邀请。创建新链接会使旧链接失效；成功完成双端信任持久化后，链接立即消费。取消、过期、传输失败或配对未完成时，临时占用会释放，允许在有效期内重试。

## 不需要自建服务器

TailSync 不提供、也不要求用户自建邀请服务器或官网链接。邀请本身携带目标 Iroh Endpoint ID 和一次性随机能力值，Iroh 负责使用当前配置的地址发现与中继/打洞路径建立 QUIC 连接。直连优先，无法打洞时由 Iroh 的中继路径承载；是否能发现和连接仍取决于两端的 Iroh 配置、网络出口、NAT 和防火墙。

因此，`tailsync://` 只是系统唤醒应用的本地链接，不是需要访问网页的 HTTP 地址。没有可用的 Iroh 地址发现或中继路径时，链接格式仍然有效，但连接会超时；这不是通过增加 TailSync 自建服务器可以绕过的应用层配对错误，需先检查网络环境或 Iroh 运行时配置。

## 协议边界与安全

- 邀请 payload 使用版本化的 `TSI1` 格式，链接使用无填充 Base64URL；另有 `TSI1-...` 粘贴兼容格式。
- Iroh 连接使用独立的 `tailsync/4/invite` ALPN。服务端先验证一次性邀请，再进入现有 Noise XX 配对握手。
- 邀请随机能力值只保存在创建端内存中的摘要；应用退出后不会恢复，链接自然失效。
- 无效链接只返回通用错误，不把邀请内容写入日志；链接本身应视为短期密钥，不要公开发布或提交到工单/代码库。
- 链接只解决“找到正确的 Iroh Endpoint”，不授予历史读取、同步或删除权限。只有验证码一致并完成双向确认后，公钥才会持久化为受信设备。

## 冷启动和热启动

Windows 通过 `tauri-plugin-deep-link` 注册 `tailsync` scheme；已运行实例由单实例转交，未运行实例由系统启动后再交给前端。macOS app bundle 在 `Info.plist` 注册同一 scheme，AppDelegate 负责冷启动和已运行实例的 URL 事件。为了避免把邀请放进事件参数，Windows 前端收到的只是“有新链接”事件，再通过本地 Tauri 命令取出经过校验的待处理值。

## 与历史页通知的关系

Windows 历史页的操作、同步和运行时错误提示现在是页面内联提示，不使用固定定位的黑色浮层，因此不会遮挡底部翻页按钮。相同语义的重复警告只增加次数，不重置过期时间；成功、警告和错误分别使用短、中、稍长的有限显示时间，并始终提供手动关闭按钮。即使不同错误持续替换，提示也最多连续显示 8 秒，随后强制留出 1.5 秒的无提示间隔，避免错误风暴让提示栏常驻。

## 验证要求

自动化门禁覆盖：

- Core：邀请编码/解码、过期、篡改、单次 claim、失败释放、双端持久化后消费，以及两个真实本机 Iroh Endpoint 之间的邀请 ALPN + Noise XX 完整配对。
- Windows：创建、检查、启动、取消命令；冷启动收件箱、热启动事件、设置页状态；Windows 原生 CI 编译；打包后启动主实例并用有效 `tailsync://` 参数启动第二实例的单实例转交 smoke test。
- macOS：Unix socket route、Swift API、`Info.plist` scheme、深链格式校验、待处理链接一次性取出、设置页创建/复制/粘贴路径。
- 跨平台：契约门禁同时检查 Windows scheme、冷/热启动接线、macOS AppDelegate 接线和 bundle scheme，任一入口漂移都会使 CI 失败。

公网环境仍属于发布前实机门禁，因为 CI 不能稳定模拟运营商 NAT、企业防火墙或强制 relay。每个候选版本必须在 Windows 与 macOS 成品包上完成下表，不能用开发进程代替：

| 场景 | 必须观察到的结果 |
|---|---|
| Windows Wi-Fi → macOS 手机流量热点（再反向一次） | 链接唤起/粘贴成功；两端验证码一致；双方确认后设备进入已配对；发送文本成功 |
| 两端处于不同普通 Wi-Fi | Iroh 建立 direct 或 relay 路径；配对后至少完成一次文本和一个小文件传输 |
| 禁止可用直连、保留 Iroh relay 出口 | 路径明确显示 relay，配对与文本传输成功；若环境无法访问 relay，必须得到有界超时而不是无限等待 |
| 接收端在点击“开始配对”前退出并于 120 秒内重开 | 重新打开同一链接后可以继续；创建端退出则旧链接必须失效 |
| 过期、取消、已成功消费的链接 | 三者都被拒绝，不能再次进入验证码确认阶段 |
| 链接冷启动与应用已运行两种状态 | Windows/macOS 都只保留一个应用实例，并自动打开设置中的远程配对区域 |

实机记录至少保留：候选版本号、两端系统版本、网络组合、最终 Iroh 路径类型、验证码一致性、是否双方持久化、失败时的完整错误文本。记录中不得粘贴邀请链接本身。
