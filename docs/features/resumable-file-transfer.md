# 跨重启文件续传

- 状态：已实现
- 适用实现：线协议 v4、数据库 schema v11
- 范围：文件和文件批次；文本与图片使用可靠事件重试，不使用本机制

## 用户语义

文件传输在网络中断、发送端退出或接收端退出后，可以在 24 小时保留期内继续。恢复位置以接收端
已有 `.part` 文件的实际长度和重新校验结果为准，不信任界面缓存或 sidecar 中的偏移。完整批次只有在
文件历史和接收回执都持久化成功后才向发送端确认完成。

以下情况不会盲目续传：源文件被修改、移动或删除；manifest 与既有批次冲突；接收存储不可用；
配对身份不再可信；保留期已过。此时 TailSync 保留可安全重试的状态或要求用户重新复制，不会把
不一致内容拼接成完整文件。

## 持久状态

### 发送端

`shared/rust-core/src/sync/outgoing.rs` 在应用数据目录的 `outgoing-transfers/` 中保存私有 journal：

- 批次 ID、文件路径、大小、内容标识和目标设备；
- 目标设备的稳定认证指纹，避免仅因设备改名而丢失待发送任务；
- 已完成目标、失败原因、重试次数和下一次重试时间；
- 2、10、30、120、600 秒的持久化退避，后续保持 600 秒，避免故障循环和重复通知。

journal 使用原子替换并同步落盘。所有目标确认完成、用户取消或记录超过 24 小时后才清理。

### 接收端

`shared/rust-core/src/sync/resume.rs` 和 `receive_engine.rs` 保存 `.part` 文件与 `.batch.json`
manifest。启动恢复时会：

1. 校验私有目录、文件名、批次上限和 manifest；
2. 从 `.part` 的实际长度推导 offset；
3. 对已经完整的文件重新执行 BLAKE3 校验；
4. 通过 `FileResume` 告诉发送端继续位置；
5. 批次完成后把文件历史、配额变更和 schema v11 接收回执放在同一提交边界内。

接收回执以认证设备指纹、批次 ID 和 manifest hash 判定幂等；`history(batch_id, batch_index)` 的
唯一约束阻止重放产生重复行。SQLite/文件事务失败时不会发送最终 ACK，发送端 journal 因而仍可重试。

## 传输与路由

每个文件以 1 MiB 块传输，块 ACK 携带下一 offset。重连后若旧连接上的在途块已经失效，接收端用
`FileResume` 触发发送端按确认位置重选路径并继续。LAN、Tailscale 和 Iroh 都复用同一 Core 状态机；
平台代码只负责连接、进度上报和剪贴板提交。

当前限制为每批最多 20 个文件、总计最多 1 GiB，单文件同样不超过 1 GiB。进度上报保持单调，
但恢复后的瞬时速率会从新采样窗口重新计算，不能把 UI 速率当作持久化正确性的依据。

## 失败与清理

- 接收存储不可用时在写入前拒绝本轮提交；发送端保留 journal 并按持久化退避重试，
  相同错误通知会节流。
- 用户停止批次时写入取消状态，并尽量通知对端；取消不是暂停，重新发送需要再次复制。
- 24 小时后会清理过期 journal、manifest 和未完成临时文件。
- 完成后的剪贴板明文副本位于 `clipboard-files/`，属于另一套短期清理策略，不是续传源。

## 验证要求

修改续传链路时至少覆盖：

- Core 的恢复、重放幂等、ACK 时序、事务失败、配额失败、稳定设备指纹和退避测试；
- macOS 与 Windows 的双向 `interop_probe`；
- Windows 原生 NSIS 打包后烟测与 macOS bundle/daemon 验证；
- 真实设备矩阵：发送端退出、接收端退出、双方先后退出、网络切换、存储拔出/恢复和源文件变更。
