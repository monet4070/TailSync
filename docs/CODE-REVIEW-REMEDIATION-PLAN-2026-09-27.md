## 2. 实施批次

每批次是一份独立可审查的 PR 候选；若同一批次触及范围过大，可按下列验收点再拆分。不要照原审查文档把多个安全、存储、UI 改动塞进一个“少于 100 行”的 PR。

### A. 信任边界：模式判定与可信设备身份

**入口**：`shared/rust-core/src/peer/directory.rs`、`shared/rust-core/src/crypto.rs`、`shared/rust-core/src/peer_cache.rs`，以及实际调用配对/换机设置的两端入口。

1. 将 Tailscale IPv4/IPv6 地址分类放在普通私网/ULA 判定之前；`lan_only` 对 `fd7a:115c:a1e0::/48` 返回 false。保留其他 ULA、链路本地和回环的既有语义，除非该模式本身另有明确定义。
2. `trust_peer_without_save` 在同 hostname、不同 pin 的情况下返回“需要明确换机/解除旧配对”，不得静默覆盖；同 pin 的重复配对保持幂等。检查调用方是否已有明确解除/重新配对流程，避免把合法换机变成无解状态。
3. 发现阶段地址只进入临时候选。对已信任设备，只有完成固定公钥验证的握手后才更新持久地址；沿用现有服务端认证后保存路径，避免为了这一点引入全面的 `AddressOrigin` 类型改造。

**验证**：覆盖 Tailscale v4/v6、普通 ULA、IPv4 私网与回环；同名异钥拒绝、同钥重复成功、明确换机成功；伪造 mDNS/UDP 地址不能改写已保存路由。检验 Windows/macOS 设置兼容旧信任记录。

**风险与回退**：同名设备的现有重配对行为会改变。旧记录不迁移或删除；若 UI 尚无明确换机入口，先补入口再启用拒绝策略。

### B. 配对可用性与读帧正确性

**入口**：`shared/rust-core/src/pairing/manager.rs`、`shared/rust-core/src/secure/handshake.rs`、现有配对测试。

1. 将失败预算仅用于有本地确认或确实证明凭证错误的情况。未经本地确认的断连、超时、取消、意外命令都释放会话而不推进全局锁定计数。保留日志和受限的按来源/总量节流，避免把“不扣预算”变成无限计算资源。
2. 未确认槽位维持 30 秒以内的硬期限。若允许新会话替换旧槽位，只允许有界且可解释的替换；已进入本地确认的槽位不可被匿名请求挤走。
3. 在 `read_pairing_frame` 中复用一个固定的读取 future。监听信号变成 true 时继续该读取；变成 false 时关闭整条连接，不重建半读的 `read_exact`；参照 [Tokio 的取消安全说明](https://docs.rs/tokio/latest/tokio/macro.select.html)。

**验证**：冻结时间测试 10 次匿名断连、异常命令、会话超时后均可正常配对；本地确认后的真实错误仍走预期安全策略；发送半个帧头/帧体后切换窗口状态，后续帧不发生字节错位。覆盖双方并发发起时的槽位行为。

**风险与回退**：锁定策略放宽后需观察匿名尝试量和 CPU；新增限流不能误伤局域网内共享 NAT 的合法设备。

### C. 预览内存上限与接收名额

**入口**：两端 `get_image_data` 命令、`shared/tailsync-runtime/src/history.rs`、`shared/rust-core/src/db/entries.rs`、`shared/rust-core/src/sync/receive_engine.rs`。

1. 预览命令先在数据库锁内仅读元数据：ID 存在、类型为 Image、长度在明确的预览上限内。类型/大小错误必须发生在打开或解密外部 payload 前。
2. 复用已有 `prepare_preview`/`preview_async` 的有界读取机制，并确认其返回形式符合两端当前 `get_image_data` 契约；若契约要求原图，显式规定大小上限和错误码，不把大文件完整装入 `Vec`。慢解密在数据库锁外执行。
3. 接收名额按唯一 receive key 计数，包含 active、pending、inflight。在同一次引擎锁持有期间完成检查和预留；建立失败、分块失败、取消、完成及进程恢复路径都释放名额。保持同 transfer ID 的幂等续传。

**验证**：文件 ID 传给图片命令时不发生 payload 读取；合法图片、超限图片和缺失 ID 的 API 契约两端一致。并发超过每对端 2 路或全局 8 路 `FileMeta` 时只有限额内请求成功；失败后可重新占用名额。测试不要求不稳定的“1ms 内返回”，而断言错误发生在读取之前且内存有界。

### D. 配对持久化一致性

**前置**：A、B 的身份和配对状态规则稳定后开展。**入口**：`pairing/manager.rs`、设置持久化结构、两端配对状态 UI。

1. 将本地已落盘但未收到对端持久化确认的记录标记为 `pending`，不要作为“已完成配对”展示或自动同步。记录对端固定公钥及会话所需的最少恢复信息；设置结构升级须兼容已有可信记录。
2. 双方均确认持久化后转为 `active`。网络中断、进程退出和 ACK 丢失保持 `pending`，提供“继续配对/重新配对”和“移除”操作；相同公钥重试幂等。
3. 不因超时自动 `forget_peer`。不能从未收到 ACK 推断对端未落盘。若考虑自动对账，先设计双方版本兼容的认证消息；第一阶段以可见、可重试状态为准。

**验证**：在本地写盘前后、发送/接收 `PairingPersisted` 前后分别断电或断线；重启后不得静默显示成功，不得删掉原已信任的同钥设备。旧版本对端不能导致永久卡住的新状态；UI 明确给出恢复动作。

**风险与回退**：这批涉及持久化格式和双端 UI，应单独评审迁移与降级。未完成记录不得悄悄获得正常同步权限。

### E. 存储配额、续传和提交后清理

**入口**：`shared/platform-network-server.rs`、`shared/rust-core/src/sync/batches.rs`、`shared/rust-core/src/db/storage.rs`、`shared/rust-core/src/db/lifecycle.rs`、`shared/rust-core/src/private_fs.rs`。

1. 先固定现有配额语义：`bulk_storage_size` 统计数据库、WAL/SHM、加密历史、incoming 与 clipboard-files 的实际占盘；系统可用空间是另一道约束。不要以删除行数代替已回收物理字节。
2. 冷启动批次预检根据相同 batch/transfer ID、manifest hash、实际 `.part` 长度计算**剩余待写明文**；长度是续传事实，sidecar 仅作校验线索。额外预留完整加密历史副本上界与安全余量，且不能重复计入已在盘的前缀或其他活动批次的承诺。
3. 在一个串行化的批次准入区间内完成读取、计算和预留，防止多个入站批次同时通过相同的空闲空间检查。沿用现有 pending 批次记账，不创建第二套不一致的配额状态。
4. 淘汰前做一次磁盘扫描。删除外部 payload 后按可确认的释放量更新计数；不确定时复测。遇仅可淘汰 SQLite 文本行而数据库文件未缩小时，停止无收益的连续删除，报告准确的物理配额不足；检查点/压缩放到可控的维护路径，并要求足够临时空间。
5. `delete_entries` 提交后的每个引用查询、路径解析和文件删除分别处理并记录错误。仅在确认不存在活跃数据库引用后对账清理孤儿文件；提交后的 WAL 检查点失败不能把已成功的删除回报成失败。
6. 将服务端 incoming 目录的裸 `create_dir_all` 改成现有私有目录助手。不要重复增加已有的 `.part` 周期清理任务。

**验证**：合法批次最多 20 文件、总计最多 1 GiB；用稀疏文件和注入式磁盘余量覆盖冷重启、半收 `.part`、旧批次并发、manifest 不匹配、固定历史不可淘汰、SQLite 不缩容、WAL busy、清理中单文件失败。检查配额不足时不会删除大量无助于释放空间的文本历史。文件权限在首次创建时为私有。

**风险与回退**：修改准入算法可能错误低估磁盘需求；必须以“剩余明文 + 最终加密副本上界 + 余量”为下界，不采用原文 700 MiB 的验收断言。

### F. ACK 与投递退避

**入口**：`shared/rust-core/src/peer/delivery/executor.rs`、`worker.rs`、投递测试。

1. 单次 ACK 超时后结束当前连接的读流，保留同一待发事件/文件状态，由 worker 在新认证连接上按既有去重和文件续传协议重试。不要在旧流上宽泛跳过不匹配序号的 ACK。
2. 心跳必须核对命令与序号；旧连接的业务 ACK 不应被用于新的心跳或下一业务帧。
3. 将握手成功但投递立即失败的路径纳入可取消退避。已有关闭信号和 `retry_wakeup` 能打断等待；保持用户主动重试的响应性。

**验证**：在发出帧后延迟首个 ACK、重复 ACK、丢 ACK、将 ACK 放在心跳前、传输中断后续传。断言没有误确认、错误协议降级或热循环；达到最长重试期限时有明确失败/警告。

### G. 连接池身份、路由刷新和文件隔离

**前置**：A 的可信身份策略、F 的重试语义。**入口**：`shared/rust-core/src/peer/pool.rs`、`delivery/worker.rs`、`delivery/race.rs`、`shared/platform-network-pool.rs`。

1. 以已固定的公钥身份（必要时加稳定本地记录 ID）标识 worker，而不是 `(动态目标, hostname)`；目标改变只更新候选快照，进行中的认证连接继续至完成/失败。明确断开、解除配对仍应关闭 worker。
2. 新候选在下一次连接竞速时使用；不能只刷新 Iroh 而让 LAN/Tailscale 永远保留旧快照。冷启动的前项快速失败时立刻释放后备延迟，健康 LAN 仍可获得短优先期。
3. 先用真实调度模型复现 S2-F5：连续文件控制帧/长 ACK 等待期间发送文字和图片，记录排队时间、失败率、用户警告。若确认线头阻塞，采用文件与即时事件两条独立认证连接，分别限流和监控；仅新增第三个 mpsc 通道不能解决同一 wire worker 的阻塞。

**验证**：传输期间切换首选 LAN/Tailscale 不重建活跃 worker 或丢待发事件；同名异钥不共池；快速失败不付固定 300ms；饱和场景满足明确的交互投递延迟目标。若不复现 F5，保留度量，不预先扩大连接数。

**风险与回退**：双连接会增加握手、FD 和状态复杂度，应作为独立后续 PR，有压力数据才实施。

### H. 本地网络发现与地址展示

**入口**：两端 `network/lan.rs`、`shared/rust-core/src/peer/directory.rs`、macOS `api/routes.rs`、Windows 地址输入校验。

1. UI 的本机 LAN 地址从正在使用的可用候选/接口中选取，不再依赖对 `8.8.8.8` 的默认出口推断。无可确认地址时展示“不可用”，绝不显示 `0.0.0.0` 为已连接路由。
2. 修复 LAN 合并时 `tailscale_ip` 被 LAN 首候选覆盖；候选排序先看已验证在线与延迟，再看接口/地址类别，最后才用稳定字符串键。虚拟网卡不能单靠私网范围识别，避免“物理 Wi-Fi 永远第一”的错误断言。
3. 当前版本对带 scope 或需要 scope 的链路本地 IPv6 明确拒绝，报可理解的 IPv4/其他可达地址提示；若后续支持，须在模型中携带 `SocketAddrV6` 的接口索引。Windows 广播枚举加入 up/p2p 过滤，并区分发包成功与发现成功。

**验证**：macOS/Windows 各测无默认网关、全局 TUN、物理 Wi-Fi 与虚拟适配器并存、断网、APIPA、IPv6 链路本地输入。确认 UI 地址与实际候选一致；实际两设备 LAN/Tailscale 连接不回退。

### I. IPC 与告警可见性

**入口**：macOS `api.rs`/`api/transport.rs`、`ApiClientRuntime.swift`，Windows `commands/platform.rs`、`useRuntimeSnapshots.ts` 及其测试。

1. macOS 通知响应增加最旧游标/丢失计数，不把合成“漏掉通知”写入容量 32 的环。客户端一个缺口只显示一次；考虑 daemon 重启后游标 epoch 变化。
2. Swift 只接受实际支持的 macOS 运行时快照平台。此为契约校验修正，不宣称已修复不存在的 Windows 守护进程重启循环。
3. Windows 隐藏窗口时暂停会消费 `sync_warning::take()` 的轮询，回到前台立即刷新，并处理隐藏前仍在途的响应。如果其他组件必须后台取快照，改为有 ID 的警告读取/显式确认；不能只把 `take` 改为 `peek`。
4. macOS `wait_runtime_snapshot` 请求加入断线取消标识；服务端取消白名单包含该命令，客户端关闭连接后许可及时归还。

**验证**：通知超过 32 条、daemon 重启、托盘停留 10 秒后再显示告警、可见性切换时在途请求、客户端断开长轮询、非 macOS 平台响应。Windows 正式安装包确认不监听旧 TCP API 19889。

6. **结论口径**：每批次报告已验证、尚待设备验证、失败与回退方式；不能把单测或同机互通称为正式发布通过。发布前另行完成签名、安装/升级和回滚门槛。

## 5. 执行顺序与停点

推荐顺序：A → B → C → D → E → F → G；H、I 可在不触碰相同文件时独立评审。C 可提前并行准备测试，但合并仍保持各批次单独可回退。G 的文件连接隔离、S3-P1-1 的隐私变更和 S4-P1-4 的性能改造都有独立决策停点，不随前置修复自动开工。

当一批回归失败、跨版本握手不兼容或磁盘模型无法证明不会低估空间时，暂停该批合并并修正设计；已合并的前置批次保持独立，不用全量回滚掩盖问题。
