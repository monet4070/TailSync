# ADR-007：以网页正文、图片和图文顺序为同步核心

- 状态：已实施（2026-10-29）；WebKit／AppKit 本机验收通过，双设备验收待完成，详见[验收记录](../acceptance/web-article-sync-2026-10-29.md)。
- 范围：网页选区的图文同步、默认恢复选择和后续验收优先级。
- 上游：[ADR-004](ADR-004-composite-clipboard-contracts.md)、[ADR-005](ADR-005-composite-content-identity.md)、[ADR-006](ADR-006-browser-image-alternative.md)。

2026-10-29 第二批：[ADR-008](ADR-008-first-publish-network-images.md) 已将有界公开图片获取接到首次事件冻结之前；沿用网络图片设置，真实网页与双设备验收仍待完成。下文“下一批”的分析保留第一批实施时的状态。

## 产品目标

用户确认的核心需求是：网页选中的正文与图片能够直接同步，图片仍在对应文字之间，数量、顺序和绑定关系正确。字体、精确字号、颜色和复杂网页排版属于次要内容，不作为基础图文同步的完成前提。

“位置正确”首先指阅读顺序和文字／图片的相对位置。首图缩略图、正文摘要或末尾统一附图不能代替完整图文。复杂 CSS 的像素级复刻不属于这一轮承诺；CSS 引起的视觉顺序差异仍须通过真实网页验收识别，不能把 DOM 解析通过直接当成页面位置已通过。

## 第一批实现

默认便携发布共用 `RestorePlan::portable_default`：

1. 原表示依赖完整时，保留 HTML 与资源绑定位置。图文文稿若同时带有纯文字 RTF，默认选用 `DocumentCompatibility`，避免目标应用优先读取 RTF 而丢图；macOS 从同一 HTML 生成原生 RTFD，Windows 可生成带嵌入图片的兼容 RTF。独立单图仍沿用原有规则。
2. 存在未闭合依赖时，复用历史恢复已有的 `AvailableContent` 路径。保留已绑定图片与其节点；缺图在原位置放占位；必要时从有界阅读模型生成独立副本，去除样式表等加载依赖。
3. 无可信正文或已保存图片，或遇到结构／预算限制，继续保留历史并拒绝自动发布。显式单格式请求保持原来的严格语义。

实时接收与历史的便携默认选择共用上述策略。自动接收仍拒绝 `MissingFormats`：当前此标签不能区分缺少可选格式与缺少承载正文的格式。历史的显式用户恢复保留既有行为，不据此放开未知来源和自动回播。

独立 PNG 只能按 ADR-006 的已有单图条件选用；不能因为字节存在，就把它猜成任意缺失 HTML 节点的图片。重复图片的每次出现仍分别绑定，不能按资源去重改变文稿顺序。

## 回执与副作用

本决策扩展 ADR-004 K6 与 ADR-006 的受限发布例外：已验证为独立可发布的图文副本可以进行一次受控写入。原始事件、wire digest、历史原件和缺失事实不变。

完整发布所选 `AvailableContent` 副本后，最终 ACK 仍为 `StoredIncomplete`；它不冒充整个来源已完整恢复，也不要求旧端理解新 wire 值。`Partial`、`Unknown`、`Superseded` 和确定无副作用的重试分支仍按原状态机执行。正文已到达不证明所有图片已到达；只有样式被简化的情况也暂保守使用现有回执，后续用户反馈语义需要单独收敛。

先持久化原始内容与 claim，再进行系统写入；继续检查授权、generation、revision 和取消。重复事件不重新写入；后台补全只更新历史，不再次自动覆盖当前剪贴板。

## 图片获取仍是独立的必要环节

本次调整解决已捕获图文及可用部分的发布规则，不会凭空获得浏览器未交付的图片字节。现有公开图片归档支持 PNG、JPEG、静态 WebP，自动归档由 `auto_save_network_images` 控制；本次不改变用户设置，也不新增联网行为。

现有后台归档及归档更新可补充历史资源，不能代替“首次粘贴已经包含全部图片”的验收。要达成直接同步公开网页完整图文，下一批必须设计在**一次自动发布之前**完成的有界图片获取，并处理事件身份、资源绑定、取消和超时；不能采用先发文字、下载完成后再自动覆盖的方法。登录图片、`blob:` 和来源未提供的懒加载图片仍需真实来源支持，不能宣称任意网页均已支持。

## 验收顺序

1. 已携带图片字节的网页：`文字 → 图片 A → 文字 → 图片 B → 文字 → 再次出现 A`，核对文本、图片内容和位置。
2. 同一内容附带不可用外链样式表：图文仍可使用，图片数量、重复出现位置不变。
3. 中间缺一张图：正文与其他图片保留，缺图占原位置，反馈不宣称完整。
4. 发布期间新复制、重复投递、部分写入和结果未知：旧任务不覆盖、不重做、不伪造成功。
5. 公开图片仅有 URL 的网页：单独验证字节获取、首次粘贴完整性和离线恢复。

macOS／Windows 原生输出的本地构造回归与真实平台粘贴、真实网络、双设备验收分别记录。不能依据单元测试通过宣布核心场景已经全面交付。

## 2026-10-29 本地验证

- 新增网页图文接收回归：两个不同图片资源、其中一个重复出现，正文内穿插图片；分别覆盖完整资源、缺图、外链样式表、样式表与缺图同时存在。核对实际物化后的 PNG 字节顺序、原始 ACK digest、历史原件与重复事件只写入一次。
- 接收副本继续区分部分写入、结果未知、新复制与缺格式；图文发布和失败状态回归在修改前失败，接通共享选择后通过。
- macOS／Windows 两种原生格式的构造输出分别与历史恢复输出逐项比对，验证三处图片的位置、重复图片和缺图占位。此项不等同于 Windows 原生运行或目标应用粘贴。
- `tailsync-core`：994 项单元测试通过、3 项跳过；默认启用的文稿语料、旧数据隔离与跨进程可靠事件集成测试通过。
- `tailsync-runtime`：134 项单元／集成测试通过，其中默认恢复计划 16 项。
- Core 接收器故障补修 11 项及来源指纹回归 1 项通过。
- macOS `clipboard::composite_capture`：31 项通过、2 项可选矩阵跳过。
- workspace 格式检查、Core／Runtime 全 target Clippy、canonical include 与跨平台契约检查通过。

测试通过隔离器运行，没有向用户 general 剪贴板或真实设备注入样本。本轮未更新已安装 App，未完成真实浏览器选区、目标应用粘贴及双设备验收。

## 原生消费补修

以上记录是第一批状态，最终本机结果见[2026-10-29 验收](../acceptance/web-article-sync-2026-10-29.md)。真实 AppKit 消费证明 HTML 加纯文字 RTF 会丢失全部图片，而仅加入 `\\pict` RTF 也不能满足 macOS 原生编辑器。因此默认路径生成 RTFD，显式 RTF 请求及历史原件不变。移除 RTF 表示时同步调整绑定的表示索引，格式排列顺序不能影响图片位置。

WebKit 的 RTFD 选区还会携带字距和描边元数据。允许简化这些已知装饰属性，继续保留正文及每次附件出现；未知语义属性仍按既有规则处理。这些变化不新增 wire 格式、设置或数据库版本。
