# Markdown 预览修复与公式验收（2026-10-29）

## 修复范围

macOS 原来使用手写块解析器和 SwiftUI Grid。表格不换行并按自然宽度展开，长单元格会把其他列推到窗口之外；列表、引用等结构也受到简化解析的限制。Windows 使用 Marked，但表格、列表、引用的专用排版缺失。

两端现共用 `shared/markdown-preview/` 的 GFM 解析规则、样式和公式策略。macOS 移除原手写块解析器；Windows 的解析与公式计算进入独立 Worker。标题、正文、嵌套列表、任务、代码、引用和表格统一排版，跟随当前主题与字号。

表格保持标题对齐、边线和隔行背景；长内容在单元格内换行，必要时仅表格横向滚动。430 px 窄窗口中整页不横向溢出。转义竖线不会拆出额外列。

公式使用本地 KaTeX，支持 `$…$`、`$$…$$`、`\(…\)`、`\[…\]`，含分式、积分、求和、矩阵及表格内公式。代码中的美元符号不作为公式，普通价格保持原样，错误公式显示源码。公式引擎、样式、字体均离线打包，不通过 CDN 加载。

## 性能与资源边界

- 原生端在 WebKit 内容进程处理；Windows 在 Worker 计算后一次安装净化的 DOM。更换条目时丢弃旧结果并清理 Worker，字号或主题变化只更新样式。
- 256 Ki 字符源码上限；macOS 桥接另有 256 KiB UTF-8 上限。上限只作用于预览，复制全部和恢复仍使用完整原文。
- 12,000 个源码 token；每表最多 500 行、32 列；最多 128 个公式，每个 2,048 字符、200 次宏展开；生成内容至多 2 MiB，DOM 至多 16,000 个元素。
- 超限时限制或退回可读源码，显示提示。Windows 解析超过 2.5 秒会终止 Worker 并显示源码，不在 UI 线程同步重试。

本机实际 WebKit 记录（单次、非跨设备基准）：

| 输入 | 内容处理耗时 | 结果 |
|---|---:|---|
| 验收文稿：中文四列表格、8 个有效公式、嵌套列表等 | 约 12 ms | 完整排版 |
| 500 行、3 列表格，18,022 字节 | 约 8 ms | 完整排版 |
| 128 个分式／根式，3,328 字节 | 约 12 ms | 完整排版 |
| 174,000 字节、重复复杂块文稿 | 约 155 ms | 命中 token 上限，退回源码 |

计时包括内容进程中的解析、公式、净化与 DOM 安装，不包含进程冷启动、字体首次解码及最终绘制，也不代表端到端延迟或所有硬件表现。

## 实际验收

使用仓内自有 `shared/markdown-preview/acceptance.md`，没有读取用户历史或修改已安装 App。

- 真实 macOS WKWebView：表格 3 行、每行 4 列；右对齐和转义竖线正确；8 个公式含 2 个块公式；离线字体加载；普通／430 px 窄窗口均无整页横向溢出。深浅主题截图已检查。普通宽度下表格宽度与可用宽度均为 700 px。
- 原生调字号后计算次数不变；切换来源不会显示旧结果；代码中的 `$x^2$` 保持代码。
- Windows 生产 React 组件在本机浏览器使用真实 Worker：四列、3 行及 8 个公式正确，完成状态明确，整页无横向溢出。此项不是 Windows 原生 WebView2 运行验收。
- 恶意 HTML、资源引用、危险链接及公式资源命令继续受限；未知公式保留源码，未开放远程图片或脚本。
