## 图片复制

用户截图对应本机历史 ID 61，时间为 15:03:04。只读元数据确认保存了 174 字节 HTML、372,137 字节独立 PNG 及本机原生归档。

此前 Core 已能选出独立 PNG，缩略图也能显示，但 macOS 的 `prepare_readable_restore` 仍把每个 `AvailableContent` 计划都当成 HTML，强制读取 `public.html` 生成 RTFD。PNG 计划因此在真实平台准备步骤报 `Readable restore has no HTML`，界面映射为通用错误。之前使用模拟平台的回归没有覆盖这个步骤。

修复让没有 HTML 的已校验计划原样进入原生发布；有 HTML 时继续做已有的依赖完整性检查和 RTFD 转换。没有增加重试或改写原件完整性。新增回归直接调用实际平台准备函数，覆盖没有原生归档的远端记录和带本机原生归档的记录。

实际验证：在安装包的 History 窗口双击 ID 61 对应行，界面反馈“已复制已保存内容，1 张图片未保存”。随后只读取本次复制的图像格式元数据，确认系统剪贴板有 `public.png`，372,137 字节、458×1000；原生 helper 的 NSImage 读回也成功。原 HTML 引用仍未归档，因此部分结果提示保留。没有把本次复制称为网页完整恢复。

## 首次启动配色

未拿到主题目录时，界面使用本地配色。该配色未显式提供浅色强调背景，构造器却把它的透明度设为与强调文字相同的 1，造成历史选中行底色过深，以及设置数值的文字和背景同色。

修复将这种派生强调背景的透明度设为 0.12；主题明确提供的不透明颜色仍保持不透明。另将启动主题读取从 `Loc.init` 移至后台第一次成功响应 ping 之后，避免后台仍在等待系统授权时就耗尽主题读取的有限重试。仍使用现有有限重试策略，没有延长重试次数。

本机通过 AppKit 查询的“减少透明度”为关闭；本轮没有更改系统显示或主题偏好。验收包替换时保留设备本地的引导选择，只更新对应的新 bundle 身份，避免本次更新被当作全新安装。
